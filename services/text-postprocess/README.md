# 转写文本整理（text-postprocess）

腾讯 ASR 输出后的本地整理层。ASR 仍走 `ssh ai` 上的腾讯适配服务，本模块只负责
拿到识别文本之后的整理。

## 目录

- `punc_core.py` — 标点恢复核心：**只回填标点，绝不改写正文字符**
- `punc_server.py` — 常驻进程，stdin/stdout JSON 协议（不开放端口）
- `models/ct-punc/` — CT-Punc 量化模型（软链到旧 CapsWriter 目录）
- `evaluate.py` — 回归评估脚本，用真实录音对比各阶段效果
- `long_eval.py` — 长句断句策略实验（分段 vs 全量），离线评测用

## 重要实测结论（2026-09-20）

**CT-Punc 接在腾讯 ASR 之后是净退化，默认关闭。**

测试集：本机 `~/Documents/CapsWriter-Voice-Dataset` 3786 条真实录音。

| 现象 | 例子 |
|---|---|
| 吞掉英文单词间空格 | `有三个 PDF 文件` → `有三个PDF文件` |
| 删掉腾讯正确的标点 | `安装、部署、使用流程` → `安装部署使用流程` |
| 丢失问号 | `是不是？你也可以考虑` → `是不是你也可以考虑` |
| 切碎英文标识符 | `走线上TTS` → `走线，上TTS` |
| 重复标点 | `全部扫描完？` → `全部扫描完。？` |
| 长数字中间插句号 | `18081` → `180。81` |

统计：200 条样本里标点减少 42 条、增加 30 条，而"增加"的样本同样是退化。
根因是分布不匹配——CT-Punc 训练来给**无标点**文本加标点，腾讯已经给过标点了，
再全量重预测就是破坏。**腾讯自带标点质量高于这个 2020 年的模型。**

因此：`punctuation` 默认 `off`。`full` 模式保留，供后续换模型时对比评估。

## 已解决的三个坑

1. **空格被吞**：不采用模型返回文本，改用双指针把预测的标点回填到原文，
   原文字符（含空格、英文标识符）一字不动。`punc_core.restore_punctuation`
2. **数字被切断**：回填时禁止在「数字-数字」「数字-小数点」之间插入标点。
   实测 200 条真实样本，正文字符（去标点去空格）改变数 = **0**。
3. **英文单词被切开**：2026-09-20 实测发现 `empty response` 被插成
   `empty respons。e`。CT-Punc 会把它认为的句读塞进英文单词中间，而这里
   属于**改写正文**（方案里的红线）。已加硬保护：相邻两个 ASCII 字母/数字之间
   一律不插入标点——真正的词边界处原文有空格，不受影响。

## 长句有没有优化空间？（2026-09-20 实测）

既然全量重预测伤的是**已经正确的短句**，那只对超长片段下手行不行？

`long_eval.py` 验证的策略 C：**以腾讯已有标点为硬边界切段，只让「去标点后长度 ≥ 阈值」
的长片段交给模型重排**，其余一律不动。腾讯的标点因此结构上不可能丢失。

300 条真实样本：

| 策略 | 改动条数 | 腾讯标点变少 | 正文被改写 | 超长片段数(≥25字) |
|---|---|---|---|---|
| A 腾讯原文 | — | — | — | 23 |
| B 全量重预测 | 160 | **85** | 0 | **38（变差）** |
| C 分段阈值 20 | 12 | 0 | 0 | 22 |
| C 分段阈值 25 | **2** | 0 | 0 | 22 |

结论：

- **B 全量**：超长片段从 23 涨到 38 —— 它把好的句子也拆坏了，确认是负优化。
- **C 阈值 25**：300 条里只动 2 条，**两条都改对了**（0 误伤），但覆盖率只有 0.7%。
- **C 阈值 20**：12 条改动里人工核对约一半是 improvements、一半是把词切开
  （如 `同样走线上TTS` → `同样走线，上TTS`），准确率约 50%，**不满足方案要求的 98%**。

也就是说：这条路安全，但**天花板很低**——真实录音里真正能从重排受益的长句只有千分之几，
而它每次都要拉起一个 965MB 的模型进程。因此 `punctuation` 仍默认 `off`，
`long_eval.py` 保留下来给以后换模型（或换 LLM 方案）时做对照。

## 标点质量审计（2026-09-20，3807 条真实录音）

用 `punc_audit.py` 直接统计 `metadata.jsonl` 里真实 ASR 输出的标点形态（不重跑 ASR）：

| 检查项 | 结果 |
|---|---|
| 完全没有标点 | **0 条**（腾讯标点覆盖完整） |
| 结尾缺句末标点 | 3 条（0.1%，都是说话中途停止造成的截断，不是标点问题） |
| 重复标点（`。。` `？？`） | **0 条** |
| 长片段（≥25 字）中间完全无断句 | 53 条（1.4%，且多为本就该连读的并列短句） |
| 超长无标点片段 | 247 个（多为代码/命令/英文短语，如 `API call failed after 3 retries`） |
| **中英混排缺空格** | **823 条（21.6%）** |

结论：**腾讯自带标点的边界判断没有系统性问题**，当初关掉 CT-Punc 的判断成立。
真正的系统性缺陷不在标点，而在**中英混排的排版**与**专名写法**：

- 中英混排缺空格：`走线上TTS就pass了`、`分功能提交commit`、`GPU的服务一直占着GPU在`
- 专名大小写不统一：`Tailscale` 实测 16 条正确 vs 15 条错写
  （`tailscale` 全小写 / `TailScale` 驼峰 / `Tail Scale` 拆开）

这两类都用 `hot-rule.txt` 的规则修正，见下一节。

**无法本地修复的一类**：极少数断句语义错误，例如
`设备上为什么有一个稳定在跑的？GPU的服务一直占着GPU在。`
——ASR 把定语切成了疑问句。这需要语义级理解，本地后处理做不到（不引入 LLM 的前提下）。

## hot-rule 新增规则（2026-09-20）

`rule_regression.js` 用**真实的 `HotRuleReplacer` 模块**跑 3807 条真实录音：
改动 **771 条（20.3%）**，规则运行时报错 0，二次应用零变化（幂等）。

| 规则（简述） | 作用 | 命中条目 |
|---|---|---|
| 汉字 + 拉丁字母 → 中间插空格 | 中英混排排版 | 491 |
| 拉丁字母 + 汉字 → 中间插空格 | 中英混排排版 | 669 |
| `[Tt][Aa][Ii][Ll]\s*[Ss][Cc][Aa][Ll][Ee]` → `Tailscale` | 四种写法归一 | 15 |
| `tcale` → `Tailscale`（词界保护） | 残缺识别 | 1 |
| `github`/`Github`/`GITHUB`/`Git Hub` → `GitHub`（排除 `/` `.` `@` 前后） | 写法归一 | 7 |

（命中数为逐规则统计，规则按顺序累加作用，数字间存在重叠）

**安全边界（`rule_edge_cases.js` 19 例全部通过）**：

- 路径与 URL 一律不动：`~/github/capswriter-agx-client`、`https://github.com/...`、`github.com`
- 连写专名不动：`GitHubDesktop`
- 项目名不动：`capswriter-agx-client`（`agx` 规则排除 `-` `_`）、`https://agx.local`
- 数字一律不动：`v1.0.22`、`第2个`、`192.168.31.134`、`18081`
- 已带空格的写法幂等，不重复插入

## 规则文件热重载（2026-09-20）

改完 `~/.config/语音转写/hot-rule.txt` **不再需要重启客户端**：每次转写前按 mtime
判断是否需要重新读盘（未变时只多一次 `statSync`），规则条数变化会打一条日志。
读取失败（文件被编辑器临时改名）时保留上一版规则，不清空——避免一次瞬时故障
让全部规则在本次会话内静默失效。

## 打包与部署（1.0.17，2026-09-20）

- `assets/hot-rule.txt` 随包内置；运行时若用户数据目录没有规则文件，会自动复制一份过去，
  之后用户只需维护 `~/.config/语音转写/hot-rule.txt` 这一处。
- `services/text-postprocess/**/*.py` 打进包内并 `asarUnpack`（外部 Python 解释器读不了
  asar 内部打包文件），但 `models/**` 被排除——那里是 965MB 的量化模型软链，不能进 AppImage。
- 包内的 `punc_server.py` 无法独立运行（缺模型），但 `punctuation` 默认 `off`，
  所以默认链路完全不依赖 Python，冷启动也不受影响。

### 尚未闭环的部分

「音频 → ASR → 整理」里的 ASR 一段依赖外部腾讯适配服务（本机无云密钥，`spark-31d6:18011`
当前也不通），目前只在**节点层**验证了「ASR 文本 → 整理」，没有跑过真实录音的端到端。
要补齐需要二选一：提供腾讯云 SecretId/SecretKey/AppId，或让 spark-31d6 上的服务恢复。

## 模型来源

旧 CapsWriter 目录 `CapsWriter-Offline-Windows-64bit/models/punc_ct-transformer_cn-en/`
里的 `model_quant.onnx` 就是官方 `funasr/ct-punc` 的量化版，但**缺 `config.yaml` 和
`tokens.json`**，原样加载会报 `The ./config.yaml does not exist`。

已补齐：从 `https://huggingface.co/funasr/ct-punc` 下载这两个文件放进 `models/ct-punc/`
（vocab 471067，与旧 onnx 输出维度 6 完全匹配）。模型本体用软链，不额外占 1GB。
