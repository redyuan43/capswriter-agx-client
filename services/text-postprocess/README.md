# 转写文本整理（text-postprocess）

腾讯 ASR 输出后的本地整理层。ASR 仍走 `ssh ai` 上的腾讯适配服务，本模块只负责
拿到识别文本之后的整理。

## 目录

- `punc_core.py` — 标点恢复核心：**只回填标点，绝不改写正文字符**
- `punc_server.py` — 常驻进程，stdin/stdout JSON 协议（不开放端口）
- `models/ct-punc/` — CT-Punc 量化模型（软链到旧 CapsWriter 目录）
- `evaluate.py` — 回归评估脚本，用真实录音对比各阶段效果
- `long_eval.py` — 长句断句策略实验（分段 vs 全量），离线评测用

## 重要实测结论（2026-09-20）

**CT-Punc 接在腾讯 ASR 之后是净退化，默认关闭。**

测试集：本机 `~/Documents/CapsWriter-Voice-Dataset` 3786 条真实录音。

| 现象 | 例子 |
|---|---|
| 吞掉英文单词间空格 | `有三个 PDF 文件` → `有三个PDF文件` |
| 删掉腾讯正确的标点 | `安装、部署、使用流程` → `安装部署使用流程` |
| 丢失问号 | `是不是？你也可以考虑` → `是不是你也可以考虑` |
| 切碎英文标识符 | `走线上TTS` → `走线，上TTS` |
| 重复标点 | `全部扫描完？` → `全部扫描完。？` |
| 长数字中间插句号 | `18081` → `180。81` |

统计：200 条样本里标点减少 42 条、增加 30 条，而"增加"的样本同样是退化。
根因是分布不匹配——CT-Punc 训练来给**无标点**文本加标点，腾讯已经给过标点了，
再全量重预测就是破坏。**腾讯自带标点质量高于这个 2020 年的模型。**

因此：`punctuation` 默认 `off`。`full` 模式保留，供后续换模型时对比评估。

## 已解决的三个坑

1. **空格被吞**：不采用模型返回文本，改用双指针把预测的标点回填到原文，
   原文字符（含空格、英文标识符）一字不动。`punc_core.restore_punctuation`
2. **数字被切断**：回填时禁止在「数字-数字」「数字-小数点」之间插入标点。
   实测 200 条真实样本，正文字符（去标点去空格）改变数 = **0**。
3. **英文单词被切开**：2026-09-20 实测发现 `empty response` 被插成
   `empty respons。e`。CT-Punc 会把它认为的句读塞进英文单词中间，而这里
   属于**改写正文**（方案里的红线）。已加硬保护：相邻两个 ASCII 字母/数字之间
   一律不插入标点——真正的词边界处原文有空格，不受影响。

## 长句有没有优化空间？（2026-09-20 实测）

既然全量重预测伤的是**已经正确的短句**，那只对超长片段下手行不行？

`long_eval.py` 验证的策略 C：**以腾讯已有标点为硬边界切段，只让「去标点后长度 ≥ 阈值」
的长片段交给模型重排**，其余一律不动。腾讯的标点因此结构上不可能丢失。

300 条真实样本：

| 策略 | 改动条数 | 腾讯标点变少 | 正文被改写 | 超长片段数(≥25字) |
|---|---|---|---|---|
| A 腾讯原文 | — | — | — | 23 |
| B 全量重预测 | 160 | **85** | 0 | **38（变差）** |
| C 分段阈值 20 | 12 | 0 | 0 | 22 |
| C 分段阈值 25 | **2** | 0 | 0 | 22 |

结论：

- **B 全量**：超长片段从 23 涨到 38 —— 它把好的句子也拆坏了，确认是负优化。
- **C 阈值 25**：300 条里只动 2 条，**两条都改对了**（0 误伤），但覆盖率只有 0.7%。
- **C 阈值 20**：12 条改动里人工核对约一半是 improvements、一半是把词切开
  （如 `同样走线上TTS` → `同样走线，上TTS`），准确率约 50%，**不满足方案要求的 98%**。

也就是说：这条路安全，但**天花板很低**——真实录音里真正能从重排受益的长句只有千分之几，
而它每次都要拉起一个 965MB 的模型进程。因此 `punctuation` 仍默认 `off`，
`long_eval.py` 保留下来给以后换模型（或换 LLM 方案）时做对照。

## 标点质量审计（2026-09-20，3807 条真实录音）

用 `punc_audit.py` 直接统计 `metadata.jsonl` 里真实 ASR 输出的标点形态（不重跑 ASR）：

| 检查项 | 结果 |
|---|---|
| 完全没有标点 | **0 条**（腾讯标点覆盖完整） |
| 结尾缺句末标点 | 3 条（0.1%，都是说话中途停止造成的截断，不是标点问题） |
| 重复标点（`。。` `？？`） | **0 条** |
| 长片段（≥25 字）中间完全无断句 | 53 条（1.4%，且多为本就该连读的并列短句） |
| 超长无标点片段 | 247 个（多为代码/命令/英文短语，如 `API call failed after 3 retries`） |
| **中英混排缺空格** | **823 条（21.6%）** |

结论：**腾讯自带标点的边界判断没有系统性问题**，当初关掉 CT-Punc 的判断成立。
真正的系统性缺陷不在标点，而在**中英混排的排版**与**专名写法**：

- 中英混排缺空格：`走线上TTS就pass了`、`分功能提交commit`、`GPU的服务一直占着GPU在`
- 专名大小写不统一：`Tailscale` 实测 16 条正确 vs 15 条错写
  （`tailscale` 全小写 / `TailScale` 驼峰 / `Tail Scale` 拆开）

这两类都用 `hot-rule.txt` 的规则修正，见下一节。

**无法本地修复的一类**：极少数断句语义错误，例如
`设备上为什么有一个稳定在跑的？GPU的服务一直占着GPU在。`
——ASR 把定语切成了疑问句。这需要语义级理解，本地后处理做不到（不引入 LLM 的前提下）。

`rule_regression.js` 用**真实的 `HotRuleReplacer` 模块**跑 3807 条真实录音：
改动 **771 条（20.3%）**，规则运行时报错 0，二次应用零变化（幂等）。

| 规则（简述） | 作用 | 命中条目 |
|---|---|---|

## 规则文件热重载（2026-09-20）

改完 `~/.config/语音转写/hot-rule.txt` **不再需要重启客户端**：每次转写前按 mtime
判断是否需要重新读盘（未变时只多一次 `statSync`），规则条数变化会打一条日志。
读取失败（文件被编辑器临时改名）时保留上一版规则，不清空——避免一次瞬时故障
让全部规则在本次会话内静默失效。

## 长文本整理（2026-09-20，v1.0.24 → v1.0.26）

超长口述自动去口水词、改明显错别字、把被 ASR 误断的句子接回、按话题分段。
实现见 `src/helpers/longTextFormatter.js`，默认走 AMD 上的 Qwen3.8-Flash-Next
（OpenAI 兼容端点 `18106`）。

### 后端选型：这件事本机小模型做不了（v1.0.26 的核心结论）

v1.0.24/25 用的是本机 ollama + Qwen2.5:3B。真实口述反馈"断句还有问题"，
逐条量化后确认**不是 prompt 没写好，是模型尺寸不够**。同一条 204 字真实口述
（中英混排）在三个后端上的表现：

| 后端 | 输出形态 | 稳定性 | 延迟 |
|---|---|---|---|
| 本机 Qwen2.5:3B（v1.0.25 现状） | 切成 7~9 行，**每行一个短句** | 5 次跑出 3 种切法 | 1.0–1.3s |
| 本机 Qwen2.5:3B + 改 prompt | 不再切碎，但中英混排时长文本会**崩成 `AMD 没 部署 ，`**（汉字被空格切开的比例 66%） | 崩坏态可复现 | 1.0–2.4s |
| **AMD 27B（现用）** | **3 段（49/69/64 字）**，`靠启动日志和。接线校验` 正确接回 | **多次跑输出完全一致** | 2.2–3.4s |

关键发现：3B 在"一字不改"时是确定的（5/5 一致），**一旦要求它判断哪里分段就
开始随机**——它没有语义判断能力，只是在标点处乱切。所以问题不在 prompt 措辞
（同一个 prompt 给 3B 随机、给 27B 稳定），在模型尺寸。

代码保留两个 provider（`openai` / `ollama`），用 `CAPS_LONG_TEXT_PROVIDER` 切换。
AMD 不可达时回退原文并记 `degraded`，不会产生坏结果。

### 关于 Qwen3 的 think 参数（仍然有效的老教训）

| 模型 | 结果 |
|---|---|
| Qwen3-4B（`think:true`） | **不可用**。思考链写了 3781 字、30 秒仍未给出答案 |
| Qwen3-4B（`think:false`） | **有害**。思考没被抑制，只是不走 `thinking` 通道，全倒进 `content`，输出涨到原文 6 倍 |

`think:false` **不等于**"不要思考"。要选架构上就没有 thinking 的模型，
而不是靠参数去关。代码里因此不传 `think`；同时 `format()` 会检查
"正文为空但 reasoning 有内容"，判为失败回退原文（`degraded: reasoning_only`）。

### prompt 形态：只修断句，禁止改写

现在的 prompt 明确三件事：删口头语、改明显错别字、**把被错误切开的句子接回完整**
（并给一个具体例子）。另外写死"禁止：替换同义词、调整语序、改写句子、增删内容"。

两条实测教训：

- **别给坏例子**。v1.0.24 的示例写成"原文两句 / 整理后两行"，3B 把示例的**形态**
  学走了——它把 ASR 的每个句号直接换成换行。小模型模仿示例的字面形态胜过理解意图。
- **"禁止替换同义词"这句不能省**。没有它，AMD 27B 会把"没走真人麦克风的一次"
  改写成"本次未使用真人麦克风"，双字组覆盖率掉到 0.72 被保真校验拦掉；加上之后
  覆盖率回到 1.000。

prompt 仍控制在 400 字符以内（有测试钉住）：给 3B 一份长规则清单，它会开始复述要求。

### 保真校验：三道关，缺一不可

prompt 写得再严也只是建议，**模型越界时必须有客户端兜底**：

| 关卡 | 抓什么 | 阈值 |
|---|---|---|
| 长度比 | 大幅增删（总结、复述、截断） | 0.70 – 1.15 |
| **逐词空格** | **崩坏态**：汉字被空格切开（`AMD 没 部署 ，`）。这类输出去标点后字数不缺、覆盖率还有 0.98，前两关都拦不住 | 汉字-空格-汉字 占比 ≤0.15 |
| 双字组覆盖率 | **等长改写**（同义替换），长度比看不见 | ≥0.90（原文 ≥80 字）/ ≥0.75（更短） |

实测四类样本的覆盖率：忠实整理 0.991 / 过度分段 1.000 / **同义改写 0.784** / 恶意总结 0.519。
注意分段不影响覆盖率（1.000），只有改词才拉低——正好是我们要抓的。

覆盖率阈值必须随长度放松：37 字删掉"所以/嘛/呢"几个口头语，覆盖率就掉到 0.83，
那是正常整理不是改写（实测被误伤过一次）。

任何一关不过就**整条丢弃、回退原文**并记 `degraded`，绝不拿模型的输出覆盖用户说的话。

### 段落规整：换行由规则兜底

`normalizeParagraphs()` 做三件确定性的事：

1. 丢空行、统一换行符，段落之间统一成**空行**（`\n\n`）—— 单换行在聊天窗口里常被
   当软换行直接合并，段就白分了
2. **上一行没断在句末标点（`。！？…` + 可选引号括号）就并回上一段** —— 断在逗号上
   的换行是噪声，不是分段
3. 去掉中文标点前后的多余空格（模型会产出 `sessionID ，` 这种），中英相邻处补一个空格

刻意**不做**"短段落按字数合并"：试过设 24 字下限往后并，结果把两句话的短文本又并回
一段，分段能力整个失效。逗号硬换行才是真问题，第 2 步已经解决。

### 终端场景必须避让

整理会插换行，而**终端里换行等于回车执行命令**。判定见 `src/helpers/terminalFocus.js`
（以 WM_CLASS 为主，标题只做兜底且排除含中文的标题）。终端场景直接跳过整理，
而不是"少分段"。

窗口判定是**三态**：`true` 是终端 / `false` 确认不是 / `null` 判不出来。
只有 `false` 才整理。**读不到窗口信息时也必须跳过**——整理是危险动作，判不出来
就不能赌。2026-09-20 端到端回放抓到过反向实现（读不到窗口照样排版），
已修并加测试钉住。非 Linux 平台没有这套判据，按 `false` 处理，不能因为没实现
就把功能整个关掉。

### 序号列举排版：这件事不需要模型（v1.0.27，v1.0.28 收紧）

用户说"第一…第二…第三…"时期望看到分行的列表。这是**结构信号，不是语义判断**，
所以用确定性规则做（`normalizeEnumerations()`，导出自 `longTextFormatter.js`），
模型不参与——即使整理服务整个挂掉，排版照样生效。

| 形态 | 识别条件 | 例子 |
|---|---|---|
| 中文序数 | `第X` + 句读标点，或 `第X` + 量词(条/点/项/款) + 句读标点/行尾 | 第一，… 第一条，… 第二点。 |
| 中文"X是" | 前面不是汉字（"统一是"不算） | 一是… 二是… |
| 阿拉伯数字 | `1.` `2、` `3)`，前一位不能是数字，后一位不能是数字 | 1. … 2. … |

⚠️ **量词后面必须跟句读标点**这条是 v1.0.28 补的，别放松回去。v1.0.27 只要求
`第X` 后跟量词，结果「第四条和第五条都要改一下」被劈成两行——**把一句话从中间
切开比漏切更糟**。这组边界是拿 3819 条真实口述语料量出来的：

| 形态 | 命中 | 处置 |
|---|---|---|
| `第X` + 句读标点 | 30（第一，×20 / 第二，×7） | 主战场，必须切 |
| `第X` + 量词 + 句读 | 2（第一条，/ 第二点，） | 保留 |
| `第X` + 量词 + 别的 | 6（**全是同句引用**：选择第二条路 / 第四项或者第五项） | 排除 |
| `第X` + 其他（第二天/第一次/第三方） | 103 | 一个都不能切 |

两条防误伤规则，缺一不可：

- **至少两个不同序号**才算列举。只出现一个"第一"时它多半是"第一次/第一版/第一台"。
- **序号前是逗号/顿号时跳过**：那说明它嵌在同一句话里
  （"第十条讲的是缓存，第十一条讲的是并发"），不是列表项的开头。
  宁可少切，也不要把一句话从中间劈开——和终端避让同一个取舍。
  （`一是/二是` 这种纯列举信号不受这条约束。）

只加换行，一个字符都不改（有测试钉住）。已经在行首的序号不重复插换行（幂等）。
和模型整理一样受**终端避让**约束：终端里换行 = 回车，不排版。

### 触发条件

- 前台窗口**确认不是**终端
- 去标点后 ≥40 字（短句分段没有意义，白等一次推理）
- 设置项：`long_text_format_enabled`（默认开）、`long_text_format_min_chars`

服务不可达时快速回退原文（超时 5 秒），不阻塞粘贴。

## M5 录音的传输失败抢救（2026-09-20，v1.0.27，v1.0.29 改成黑名单）

**问题**：20:10:49 那次会话，用户说了 45 秒，前 33 秒音频正常上传，设备最后
在 stop 请求里报 `upload_failed: true`。客户端把它当"录音失败"处理，主进程发
`external-recording-cancel`，渲染层据此把实时转写结果连同 PCM 缓冲一起丢掉。
**数据集里留下 45 秒空白**——而那次的实时识别其实已经转出了 173 字。

**根因**：「传输没走完」和「内容无效」是两件事，原来的代码把它们混成一个。

**修法**（`src/helpers/m5VoiceBridge.js`）：

- `shouldSalvageSession()` 判定是否值得抢救，三个条件缺一不可：
  ① **不是"主动放弃"类的中断**（见下）② 已收到 ≥1 秒音频
  ③ 音频已经派发给渲染层（渲染层手上才有实时转写文本，主进程只有 PCM）。
  另外限 `device_upload` 路径（本机采集另有一套蓝牙/音频路由恢复逻辑，不去插队）。

  ⚠️ **判定是黑名单（`NON_SALVAGEABLE_FAILURE_REASONS`），不是白名单。**
  v1.0.27 第一版写成了白名单（只认 4 个错误码），那样每遇到一个新的失败原因
  就要补一个字符串——补漏一次就等于把这个 bug 又放回来一次。而用户的判断标准
  是"**只要已经产出过内容就不能整段丢**"，那是一**类**问题。
  黑名单只列明确不该救的：

  | 不救的原因 | 为什么 |
  |---|---|
  | `bridge_recovery` / `renderer_recovery` | 渲染层正在重建，拿着文本的那一方已经不在了，发 stop 过去没人接 |
  | `session_preempted` / `user_cancelled` / `recording_cancelled` | 主动放弃，不是意外中断（用户取消本来也不走 `abortSession`，这里是防御性兜底） |

  没见过的失败原因**默认救**——有测试钉住（`some_future_failure_mode` 必须返回 true）。
- `salvageSession()` 做和正常收尾一样的资源清理，**只改一处：不发 cancel，
  改发带 `salvage: true` 的 stop**，让渲染层交出手上的文本
- 渲染层收到 `salvage` 标记时用 `selectSalvagePayload()` 取最近一次 partial 当结果
  （**不等 final**：设备已经不再上传音频，等下去只会拖到超时），
  之后走原本的粘贴 + 数据集留存链路
- `preserveSessionPcm()` 把已收到的 PCM 转成 WAV 落盘到
  `<userData>/salvaged-recordings/`。原来的 spool 文件 60 秒后就被删，
  抢救场景下那是最后一份原始音频
- 20 秒没收到渲染层回传则兜底收尾，避免会话挂在 `salvaging` 状态

**验证**：`services/text-postprocess/m5_salvage_replay.js`（不用 mock）——
真 `M5VoiceBridge` + 真 HTTP + 真实录音 + 真 CRC32 分块上传 + **落盘的 WAV 送真
ASR 服务重新识别**。模拟 45.6 秒录音只传上 80%：

```
旧行为：这次会话产出 0 字
新行为：抢救出 147 字（真实 ASR 识别，与原文字双字组覆盖率 0.869），音频留盘
```

## 打包与部署（1.0.17，2026-09-20）

- `assets/hot-rule.txt` 随包内置；运行时若用户数据目录没有规则文件，会自动复制一份过去，
  之后用户只需维护 `~/.config/语音转写/hot-rule.txt` 这一处。
- `services/text-postprocess/**/*.py` 打进包内并 `asarUnpack`（外部 Python 解释器读不了
  asar 内部打包文件），但 `models/**` 被排除——那里是 965MB 的量化模型软链，不能进 AppImage。
- 包内的 `punc_server.py` 无法独立运行（缺模型），但 `punctuation` 默认 `off`，
  所以默认链路完全不依赖 Python，冷启动也不受影响。
